# 自己的 wasm：下一代目标

## 要解决什么

页面用的是 Node/浏览器的 wasm 运行时（V8），它不给可执行内存，所以 copy-and-patch 用不上。页面吞吐停在 31 Mips（解释器），native 的 JIT 有 4794 Mips 的理论块吞吐。

问题一句话：**怎么让页面也吃到 JIT 的收益。**

## 三条路

**甲：自己写一个 wasm 运行时（解释器）**
把 wasm 字节码解释执行，替掉 V8。工程量约 150 条指令、内存模型、表与函数调用、异常、SIMD 可选。
不可行的理由：自己写的解释器比 V8 慢，而 V8 是带 JIT 的。等于把「页面慢」从 guest 解释器搬到 wasm 解释器，问题还在。

**乙：自己生成 wasm 模块（运行时 WebAssembly.compile）**
把 guest 基本块直接翻成 wasm 函数字节码，运行时编译加载，页面调用。这就是「wasm 侧的 copy-and-patch」——模板不是机器码而是 wasm 字节码，洞还是立即数和寄存器槽位。
关键问题：`WebAssembly.compile` 每次调用的延迟（毫秒级？），决定它只能用于热块。
难点：需要一个 wasm 二进制生成器（汇编器），负责编码、类型段、函数段、代码段、导出。

**丙：混合**
页面保留解释器跑冷路径，热块走乙；native 走现有机器码 JIT。两套后端共享同一份「模板 + 洞」描述，只是最终编码不同。

## 判断

推荐 **乙**，理由三条。

第一，它继承了 copy-and-patch 的骨架：模板 + 洞 + 块，与 native 侧同构，知识可复用。

第二，它不需要写 wasm 解释器，V8 的 JIT 替我们做优化，生成的是字节码而不是机器码，安全模型允许。

第三，它可以渐进：先生成「块」，热了才编译，冷路径完全不动。

## 拆解（乙）

1. **wasm 生成器骨架**：最小模块（一个函数、一个导出），能 `WebAssembly.compile` 并调用。
2. **模板映射**：把 native 的模板表映射成 wasm 函数模板（寄存器槽位在 wasm 里是 linear memory 偏移）。
3. **块翻译**：guest 基本块 → 模板序列 → wasm 函数体。
4. **缓存与热度**：块按需编译，带引用计数；冷块回收。
5. **回退**：任何不支持的指令 → 整块回退解释器。
6. **对照**：同一段 guest 代码，解释器 / wasm-JIT / native-JIT 三方吞吐。

## 风险

- `WebAssembly.compile` 的延迟可能吃掉收益；需要先用一个最小实验测出来（这条是 go/no-go）。
- 生成器的调试成本高（字节码错误只能看 wasm 反汇编）。
- wasm 里没有寄存器，所有 guest 寄存器都是 linear memory 访问；这是与 native 模板最大的差异，吞吐会低于 native JIT。

## 与现有工作的关系

- native JIT 继续推进（翻译器已有 mov/add/sub/and/or/xor/ret）。
- wasm 生成器复用同一个 `TranslatedInsn` 抽象，只是后端换成 wasm 编码器。
- 页面短期维持解释器，不阻塞。

## 下一步

先做「go/no-go 实验」：一个最小 wasm 模块（add 一个常量），测 `WebAssembly.compile` 的延迟与调用开销。延迟可接受再投入生成器。
