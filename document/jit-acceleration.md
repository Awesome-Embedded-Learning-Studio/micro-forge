# native JIT 加速：卡点与三条出路

## 现状

- JIT 机制正确：编译、执行、结果与解释器一致，失败块有缓存，批量 retire 已做。
- 覆盖率 0.1%：内核 1 亿条指令里只有 8.6 万条经过编译块。
- 三个模板（mov imm32、mov reg,reg、lea base+disp）加完，覆盖条数一个字节没多。

根因是内核的指令流以内存访问、算术和跳转为主，而模板集只有寄存器类指令。继续加寄存器模板没有意义。

## 为什么内存模板难

内存指令需要 vaddr 到 paddr 的翻译，而翻译在 C++ 侧的 MMU 里（TLB、页表、权限）。JIT 模板是一段固定机器码，没法直接调用 C++ 的 `translate_access`，除非安排调用约定。

## 三条出路

**甲：模板调用 C++ 助手**

模板里 `mov rdi, regs; mov rsi, vaddr; call helper`，helper 做翻译和读写。

- 每访问一次内存一次函数调用（约 5-10 周期）。
- 解释器里同样的访问也要 translate + bus resolve，所以调用开销未必是净损失。
- 需要一个全局的 CPU 指针供 helper 取状态，或者把 CPU 指针当参数传。
- 工作量小，是能最快验证「内存模板值不值」的办法。

**乙：把 TLB 查找搬进模板**

模板里直接对 TLB 数组做查找（比较 tag、取 frame、拼物理地址），命中走快路径，未命中 call 慢路径。

- 快路径无函数调用，最接近真实 JIT 的形态。
- 需要把 TLB 的内存布局固定下来（数组地址 + 步长 + 有效位位置），并保证失效时同步。
- 工作量中等偏大，但收益最确定。

**丙：临时关闭分页做 flat 映射**

仅对「关闭分页的 guest」生效。长模式下无法关闭分页，所以只适用于 32 位保护模式或实模式。

- 不适用于当前内核。
- 可以作为「未来 32 位模式」的副产品。

## 甲方案的调用约定（细化）

模板与 helper 的约定，写死下来避免实现时反复改：

- 参数：`rdi = Cpu*`，`rsi = 虚拟地址`，`edx = 访问宽度（1/2/4/8）`。
- 返回：`rax = 读出的值`（写操作返回 0）。
- helper：`Cpu::jit_load` / `Cpu::jit_store` 两个公开方法，内部复用
  `translate_access` + `bus_`，失败时 latch fault 并返回 0。
- 模板形态（mov reg,[base+disp]）：
  `push rdi`（保存寄存器基址）→ 算地址进 rsi → `mov rdi, <Cpu*>` →
  `call <helper>` → `pop rdi` → 写回目标槽。
- helper 调用使用 `movabs r11,<helper64>; call r11`，编译器向 `call_offset`
  指向的 imm64 洞写完整地址，支持 PIE 宿主。五个模板的逐字节布局见
  [PIE helper 调用说明](notes/jit-pie-helper-calls.md)。

## 推荐

先做**甲**，用实测回答「内存模板到底值不值」。如果 call 开销吃掉收益，再上**乙**；如果甲的收益已经为正，就先停在甲。

## 验收标准

- 覆盖率从 0.1% 提到 30% 以上。
- 内核启动吞吐超过解释器（当前 7.4/10.3 Mips 是基线）。
- 九段验收全绿，JIT 默认仍关闭，由 `MICRO_FORGE_JIT` 打开。

## 差分结论（第 25 轮）

- mov-only 程序：JIT 与解释器 rip/寄存器/flags 完全一致。
- mov + 两条 add：同样完全一致（rax=0xC、rcx=0x122、flags 相同）。

所以模板语义没有问题，helper 调用约定也正确。内核仍然挂住，问题不在
模板本身，而在块边界：JIT 块从任意 rip 起步（包括数据区），而数据区的
字节被当成指令编译后，块内的 helper 调用会带着错的 slot/imm 执行。

对比：解释器在数据区也会解出乱指令，但它单步执行、每步都重新取指；
JIT 一次执行整块，乱指令多了就会崩或挂。

候选修法逐条评估（第 26 轮）：

1. **只对代码段编译**：放弃。Cinux 的 kernel.bin 是 flat binary（非
   ELF），loader 里没有任何段信息，代码与数据在物理上不可区分。
2. **块执行后校验 rip**：放弃。挂/崩发生在块执行过程中，事后的校验
   无法撤销已经跑完的整块。
3. **寄存器合法性检查**：难。guest 寄存器本来就可以是任意 64 位值，
   没有可靠的「非法」判据。
4. **只编译纯寄存器模板**（拒绝 helper 模板）：可行但无收益。数据区
   的块不再崩（纯模板乱跑不会调 helper），但覆盖率仍然只有几个百分点，
   等于关掉 JIT。

## 结构性结论

native JIT 的瓶颈不是模板，也不是 flags，而是 **flat kernel 里代码与
数据在同一物理空间**：guest 会因为栈/指针错乱跳到数据区，解释器单步
执行只是走偏，JIT 一次跑完整块就会崩或挂。

要让 native JIT 真正安全地加速，前提是能区分代码与数据，也就是需要
ELF 段信息、符号表或可执行页标记。这属于 loader/内核格式层面的事，
不是 JIT 自身能解决的。
