# JIT 覆盖率从 75% 推到 99.96%：阶段总结（2026-11-13）

## 演进

| 阶段 | 老内核 | 关键改动 |
|---|---|---|
| 起点 | 75.00% | mov 族、基础 ALU、内存形式 |
| 块链接 | 79.60% | ret/leave/call/jmp/jcc 各自独立成批 |
| 补形态 | 80.54% | call reg/rel32 |
| 控制流 | 97.91%* | jmp/jcc，块不再逐条截断 |
| 修正统计 | 96.57% | 修"块吞指令"的虚高（*那 97.91 含虚增） |
| 索引寻址 | 97.09% | add/sub reg,reg、movzx 索引 |
| 累加器短形式 | 97.46% | kImplicit 放行、lea r32 |
| 权重榜 | **99.09%** | bt、cmov 内存形式（各 21 万次回退） |
| 内存立即数 | 99.75% | not、ALU [mem],imm、imul [mem] |
| 端口 I/O | 99.94% | in/out 复用 execute_ports |
| 位操作 | 99.95% | movsx、neg、bts/btr/btc |
| 索引标志位 | 99.96% | test/cmp 的 SIB 形式 |
| 系统指令 | **99.96%** | lgdt/lidt/rdmsr/cpuid/pushfq |

## 三个改变效率的转折

**一、块链接（97.9% 那一跳）**。jcc 之前，每条条件跳转都把块切断，后面的
指令全部落回解释器。两条出口打通之后覆盖率单轮涨 17 个点——这不是因为
jcc 本身多，而是因为块终于能连起来了。

**二、修正统计口径（96.57%）**。块尾模板自带宿主 ret，但终止逻辑写错成
"减预算后只跳出 switch"，于是块把后面最多 64 条指令也打包进来，从未执行
却计入覆盖率。修完数字反而降了 1.3 个点——那才是真实值。**统计虚高比低
覆盖更危险**，因为它会让人以为已经做到。

**三、按执行权重排序（99.09%）**。此前挑目标看"编译失败次数"，那个数字
数的是"多少个不同 rip 失败了"。lgdt 编译失败 34 次排第一，可它只在启动
时跑一次；bt 和 cmov 内存形式各被执行 21 万次。换成按回退次数排序之后，
两批改动就是 1.5 个百分点。

## 现在的剩余

99.96%，回退 11,154 次，355 个失败块。构成：

- 启动路径上每条只跑一两次的杂项指令（占绝大多数）
- 需要建模架构状态的：iret（弹五值改控制流）、fxsave64（512 字节浮点
  状态）、少数段寄存器操作

每项的成本是 20 到 100 行，收益是 0.0001 到 0.002 个百分点。**这就是
"几乎 100%" 的实际含义**：不是做不到，而是剩下的每一条都在启动路径上
跑一两次，做与不做对实际运行没有可测量的影响。

## 方法上值得留下的

- **重建指令形状复用解释器**：`execute_grp3` 只读助记符与宽度、
  `execute_imul23` 还读三个操作数、`execute_ports` 读端口操作数、
  `execute_system` 读内存操作数——只要在 helper 里拼出它需要的形状，
  复杂的语义（除法、标志、设备副作用、控制寄存器）就只有一份实现。
- **端口 I/O 与设备副作用绝不能有第二份**：串口输出走 `execute_ports`，
  这是双引擎 console 逐字节一致的根基。
- **洞偏移按实际编码长度累加**：`48 89 84 27` 是四字节不是三字节。这类
  错误的表现是"失败块数反而变多"，因为新模板被校验器拒了。
- **有统计再动手**：`MICRO_FORGE_JIT_FAILSTATS` 的两个层次（编译失败
  清单、回退次数排行）各自解决不同的问题。
