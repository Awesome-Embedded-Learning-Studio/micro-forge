# 累加器短形式与 lea r32（2026-11-12，118b50e）

## kImplicit 是被守卫挡掉的

`48 3D 00 01 00 00` 是 `cmp rax, 0x100`，寄存器编码在 opcode 里，解码器
给出的 `ops[0].kind` 是 **kImplicit** 而不是 kReg。translate 里那道"目标
必须是通用寄存器"的守卫只认 kReg，于是这类短形式全部落回解释器。

放行 kImplicit 之后（`operand_slot` 对它本来就能用），cmp/test/add 等一族
短形式同时进入通用 ALU 路径，失败块一次少了 71 个。

这也说明一件事：**守卫写"必须是某种 kind"时，要把解码器可能给出的所有
kind 想一遍**。kImplicit 专门用于"表语义决定、不来自 modrm"的操作数，
累加器短形式是它最常见的来源。

## lea r32 的模板

`kLeaSlot32`（20 字节）：`mov eax,[rdi+base32]`（读寄存器槽的低 32 位）、
`add eax,disp32`、`mov [rdi+dst32],rax`（整槽写）。32 位运算的结果天然
零扩展到 64 位，正好是 x86 lea r32 的写语义。

## 洞偏移又数错

`48 89 84 27` 是**四个字节**（REX + opcode + modrm + SIB），所以紧跟的
位移洞从 @16 开始，我按 @15 写。`has_valid_layout` 返回 false 时不会
告诉你是哪个洞，表现只是"块编译失败"，于是失败块数反而比改动前多了
96 个。

定位办法：写个 standalone，把 `code` 逐字节和 patch 的偏移一起打印出来，
一眼看到 `code[15] = 0x27`（SIB 字节）而不是 0。

**手算洞偏移的老规矩再强调一次**：按每条指令的**实际编码长度**累加，
modrm 后面还有 SIB 的要额外加一字节。

## 结果

老内核 97.39% → **97.46%**，新内核 97.44%，双内核 console 逐字节一致。
312 差分用例，九段验收全绿。失败块 659 → 556。

剩下的是 div、iret、lgdt/lidt、fxsave64、rdmsr 这类需要建模架构状态的
指令，每项的编译失败次数都在 12 上下，已经进入"一条一条啃"的阶段。
